## Now

### LIV-02 — Live commands and role projection

- **Outcome:** a DM socket activates and deactivates the live scene and adds, moves, hides, reveals and deletes its tokens over the WebSocket; the server validates each command against a registered payload schema, applies it last-write-wins and emits to each room exactly what `04` §3 states: activation a fresh snapshot per role (D-039), deactivation `scene.cleared`, a reveal `token.added` and a hide `token.removed` to players, a hidden token's add, move or delete nothing to players (`04` §2, `04` §3, `04` §4); live tokens are numbered as in preparation, the rename of a lone token reaching both rooms (G-023); players' events carry the strict player token shape with a stacking rank among visible tokens (G-025); a request without a DM session fetches only the display version of the live map and of visible tokens' images, read per request, so hiding, deactivating, activating another scene or replacing the map revokes at once (`07` §5, G-020).
- **Specs:** `13` §6 LIV-02, `04` §2, `04` §3, `04` §4, `04` §5, `07` §3, `07` §5, `05` §3, `05` §4, `10` §3; D-019, D-039, D-049, D-064, D-099, D-104, D-105, D-106, D-108; Q-012, Q-014, Q-047, Q-083, Q-092, Q-093.
- **Dependencies:** LIV-01 (rooms, snapshots, versions, D-104 to D-106); Q-093 answered: one version counter per room, an event advancing only the rooms it reaches (D-107, D-108).
- **Acceptance (executable):**
  - Vitest against a real SQLite file and a real Socket.io client: each of `token.add`, `token.move`, `token.setVisibility`, `token.delete`, `scene.activate` and `scene.deactivate` has a strict payload schema and changes the database as `04` §2 says; an invalid payload is refused in the envelope and changes nothing; two DM sockets' conflicting moves end last-write-wins; each command's events reach each room as `04` §3's table states, the players' payload keys exactly `PlayerTokenSchema`'s, adding or moving a hidden token sending players nothing and hiding sending exactly what deleting sends (Q-083); each room's versions ascend over the wire without a hole across real events, a hidden token's events advancing only the `dm` room's (Q-093, D-108); revealing a second token of an asset live shows "Goblin 1" and "Goblin 2" on a player socket (G-023, Q-092); preparation REST writes to the live scene stay refused (D-100).
  - Gates of `10` §3, each test carrying its marker and its tripwire promoted in CI: `@gate:player-command-rejection` (every command type from the players room refused and nothing changed, over the wire); `@gate:image-revocation` (an image a player fetched is refused after its token is hidden, after deactivation, after another scene is activated, and after the live map is replaced while the old image stays referenced, G-020); the recorded-traffic test of every message and image response a player socket receives across adding hidden tokens, revealing, hiding, moving, deleting, activating another scene and reconnecting, with no hidden token's id, asset, image or count in it (`@gate:hidden-information` once it also covers undo, LIV-05, or by a recorded decision).
  - Playwright: a DM context activates a scene through the socket and a player context receives its snapshot (drawing it is LIV-03); `make verify` exit 0 on both CI runners; `TRACEABILITY.md` LIV-02 row with test names.
- **Non-goals:** drawing the live scene on the player view (LIV-03); live mode, Go live and Blank TV controls in the DM view (LIV-04); undo (LIV-05); cameras (LIV-06); the ruler (LIV-07); pushing live setup edits as snapshots (LIV-04, G-019).
- **Review:** `Surfaces: security, scope, ux`, `Touches red line: yes`, `Contract change: yes`, so prompt 2 (review) runs after implementation.
