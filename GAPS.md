# GAPS

Deliberate incompleteness and missing infrastructure. A gap is closed only by evidence, never by a stub. Each row names the evidence that closes it and the plan item that produces it. IDs are never reused: a closed gap's row is removed and its ID retired. `make check-docs` verifies that every cited work package and phase exists.

| G-001 | FND-01 delivered the command contract and the scaffold; FND-03 added the conventions: the shared error envelope and schema validation for REST, the WebSocket command and event envelopes with the version counter, and the redacting logger. SRV-01 added the schema of the eight entities (migration 0001) and their contract types in `shared`. SRV-02 added the PIN, DM sessions, the lockout and the session guard on every `/api` route, with `/api/auth`, `/api/setup`, `GET /api/settings` and `PUT /api/settings/pin` (D-076). SRV-03 added campaigns, sessions and scenes over REST: CRUD, ordering, duplication and confirmed, cascading deletion (D-078); SRV-04 added the image upload pipeline, image metadata and presets, and the image files, which only a DM session can fetch until LIV-02 adds the players' entitlement (D-080); SRV-05 added the shared asset library over REST: CRUD with lower-case tags, search and filters, usages and the refusal to delete an asset in use, and an image change that every token of the asset follows, and start-up removes images nothing references (D-083, D-084); scene setup and tokens while not live (`/api/scenes/:id` beyond rename and delete) are not served yet. | G-003 | On Windows, CI runs the gate targets (`lint` to `scan-secrets`) through MSYS2's `make` and bash and they pass (FND-02, D-060), but `make dev` and `make clean-start` are not in CI: `scripts/clean-start.sh` uses `setsid` and `tar`, which Windows has only through MSYS2, Git Bash or WSL, and macOS lacks `setsid`. | A Windows developer may be unable to run `make clean-start` or `make dev` as written; the server itself is plain Node and runs natively (the Windows `e2e` job starts it with `npm start`). | A recorded run of `make dev` and `make clean-start` on Windows, or a recorded decision on how Windows runs them. | REL-02 |
| G-007 | The views have no loading, reconnecting or load-failure state. `client/src/main.tsx` renders nothing until the view's chunk arrives, and a chunk that fails to load (the server stopped, or restarted with a new build between the page and its script) leaves the dark background with an unhandled rejection and no message. The error boundary covers only a view that throws while rendering, and the DM error screen's Reload button is tested by click in jsdom, not by the keyboard gate, because the production build has no way to make a view fail. PRP-01 part 1 gave the DM view one state of its own: while it asks the server whether a PIN exists and whether it is signed in it says it is loading, and when that request fails it names the reason and offers Try again (D-085); a chunk that fails to load, the player view and reconnecting are still open. Found by the FND-04 review, 2026-09-24. | A DM whose laptop loses the server mid-load sees a blank page with no way out but the browser's reload; the TV shows the dark idle background, which is harmless. | A loading and a load-failure state for both views, and the reconnecting state of `04` §6, each rendered from the catalogue and covered by tests; the DM's failure state reached and operated in the keyboard smoke test. | LIV-01 |
| G-008 | Every database backup (`09` §2) keeps the PIN hash that was current when it was taken, including one from before a `reset-pin` or a PIN change. SRV-02 closed the other half: `settings` is read through explicit column lists, `GET /api/settings` is serialised through the strict `SettingsSchema`, and `server/src/http/auth.test.ts` "carries the hash in no /api response" (D-076). Found by the SRV-01 review, 2026-09-24. | A copied data directory or backup carries old hashes, crackable offline for a 4–8 digit PIN. | The README (REL-01) states that backups hold the PIN hash and how to remove old ones. | REL-01 |
| G-010 | The lockout of `07` §6 is per client address (Q-009), so a LAN client that changes its IPv4 address gets 5 fresh guesses per address: about 1,250 in the first minute from a /24, and a 4-digit PIN within hours. Nothing bounds failures across addresses. IPv6 cannot reach the server today (it listens on `0.0.0.0`); if it ever listens on `::`, keying by the full /128 would make the lockout trivial to bypass. Found by the SRV-02 review, 2026-09-24. | A determined device on the Wi-Fi can still guess a short PIN in one evening. | An owner decision (a question card: a server-wide failure budget, IPv6 keyed by /64, or the accepted residual risk stated in the README), then its test. | REL-01 |

| G-017 | Upload residuals the SRV-04 review deferred, each open only to a DM session or to the DM's own PC. A browser sends the whole body before it reads the answer, so a DM uploading an oversized file waits for all of it to be sent and discarded before seeing the 413 (D-082), and a body still arriving 30 s after the refusal has its connection cut, which the browser shows as a network error; an upload sent with `Expect: 100-continue` and a declared length over the limit is told to continue by Node before the route refuses it. Nothing bounds concurrent uploads or the total size of the images folder, and a PNG under sharp's pixel limit (about 268 megapixels) decodes line by line but still costs CPU. A second server started on the same data directory empties `images/.incoming` at start-up (`prepareImagesDir`) and fails the first server's uploads in progress, before it fails to listen on the taken port. Found by the SRV-04 review, 2026-09-24. | On a slow link an oversized map takes long to refuse, or ends in a network error; a DM can fill the disk only by uploading; two servers on one data directory lose an upload in flight, not stored data. | The scene-map upload checks a file's size against `upload_limit_bytes` before sending it and names the limit (PRP-02), as the library's asset form already does (PRP-01, D-088, `client/src/dm/library/Library.test.tsx` "refuses a file over the upload limit before sending anything, naming its size and the limit (G-017)"), with a component test; a `checkContinue` handler answering 413 before the body for a declared length over the limit, with a real-connection test; the README (REL-01) states one server per data directory and that the images folder grows with uploads; or a recorded decision that accepts them. | REL-01 |
