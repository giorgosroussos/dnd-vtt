# GAPS

Deliberate incompleteness and missing infrastructure. A gap is closed only by evidence, never by a stub. Each row names the evidence that closes it and the plan item that produces it. IDs are never reused: a closed gap's row is removed and its ID retired. `make check-docs` verifies that every cited work package and phase exists.

| ID | Gap | Consequence | Evidence to close | Plan item |
| --- | --- | --- | --- | --- |
| G-001 | FND-01 delivered the command contract and the scaffold; FND-03 added the conventions: the shared error envelope and schema validation for REST, the WebSocket command and event envelopes with the version counter, and the redacting logger. SRV-01 added the schema of the eight entities (migration 0001) and their contract types in `shared`. SRV-02 added the PIN, DM sessions, the lockout and the session guard on every `/api` route, with `/api/auth`, `/api/setup`, `GET /api/settings` and `PUT /api/settings/pin` (D-076). SRV-03 added campaigns, sessions and scenes over REST: CRUD, ordering, duplication and confirmed, cascading deletion (D-078); SRV-04 added the image upload pipeline, image metadata and presets, and the image files, which only a DM session can fetch until LIV-02 adds the players' entitlement (D-080); scene setup and tokens while not live (`/api/scenes/:id` beyond rename and delete) and assets are not served yet. There is no WebSocket server or room, and no command payload schema, so the process command validator refuses every command as `command_unsupported` until LIV-01 onward register payload schemas (D-064). FND-04 made the views shells: the DM view at `/dm` is a banner, a skip link and a main landmark with no workspace (PRP-01), and the player view at `/` is the idle screen, which never switches to a live scene and does not hide the cursor yet (LIV-03). The CI pipeline of FND-02 runs every gate on Linux and Windows. SRV-04 awaits its CI run and review; every work package after it in `specs/13-implementation-plan.md` is unstarted. | No product behaviour in the specifications is verifiable yet; only the gates and the conventions are. | Per-package rows in `TRACEABILITY.md` moving to `done` with command and test evidence. | Phase 1 onward |
| G-002 | The model and webOS version of the owner's LG TV, the player view's acceptance device, are not known. | The display-version size cannot be confirmed and the TV acceptance run cannot be planned against a known browser. | The model or webOS version recorded in `docs/inputs/` and the acceptance run of `10` §4 passing on it. | REL-03 |
| G-003 | On Windows, CI runs the gate targets (`lint` to `scan-secrets`) through MSYS2's `make` and bash and they pass (FND-02, D-060), but `make dev` and `make clean-start` are not in CI: `scripts/clean-start.sh` uses `setsid` and `tar`, which Windows has only through MSYS2, Git Bash or WSL, and macOS lacks `setsid`. | A Windows developer may be unable to run `make clean-start` or `make dev` as written; the server itself is plain Node and runs natively (the Windows `e2e` job starts it with `npm start`). | A recorded run of `make dev` and `make clean-start` on Windows, or a recorded decision on how Windows runs them. | REL-02 |
| G-007 | The views have no loading, reconnecting or load-failure state. `client/src/main.tsx` renders nothing until the view's chunk arrives, and a chunk that fails to load (the server stopped, or restarted with a new build between the page and its script) leaves the dark background with an unhandled rejection and no message. The error boundary covers only a view that throws while rendering, and the DM error screen's Reload button is tested by click in jsdom, not by the keyboard gate, because the production build has no way to make a view fail. Found by the FND-04 review, 2026-09-24. | A DM whose laptop loses the server mid-load sees a blank page with no way out but the browser's reload; the TV shows the dark idle background, which is harmless. | A loading and a load-failure state for both views, and the reconnecting state of `04` §6, each rendered from the catalogue and covered by tests; the DM's failure state reached and operated in the keyboard smoke test. | LIV-01 |
| G-008 | Every database backup (`09` §2) keeps the PIN hash that was current when it was taken, including one from before a `reset-pin` or a PIN change. SRV-02 closed the other half: `settings` is read through explicit column lists, `GET /api/settings` is serialised through the strict `SettingsSchema`, and `server/src/http/auth.test.ts` "carries the hash in no /api response" (D-076). Found by the SRV-01 review, 2026-09-24. | A copied data directory or backup carries old hashes, crackable offline for a 4–8 digit PIN. | The README (REL-01) states that backups hold the PIN hash and how to remove old ones. | REL-01 |
| G-009 | Tags are unique per asset case-sensitively (`Cave` and `cave` both insert), which the specifications do not settle. SRV-04 closed the other half: every upload writes `image.variants` as `{ display, thumbnail }` with width and height, and `server/src/http/images.test.ts` validates it against `ImageVariantsSchema` (D-080). Found by the SRV-01 review, 2026-09-24. | The tag filter of `05` §1 could show two tags that look the same. | SRV-05 decides tag case (a `COLLATE NOCASE` migration or normalisation in the route) with a test. | SRV-05 |
| G-010 | The lockout of `07` §6 is per client address (Q-009), so a LAN client that changes its IPv4 address gets 5 fresh guesses per address: about 1,250 in the first minute from a /24, and a 4-digit PIN within hours. Nothing bounds failures across addresses. IPv6 cannot reach the server today (it listens on `0.0.0.0`); if it ever listens on `::`, keying by the full /128 would make the lockout trivial to bypass. Found by the SRV-02 review, 2026-09-24. | A determined device on the Wi-Fi can still guess a short PIN in one evening. | An owner decision (a question card: a server-wide failure budget, IPv6 keyed by /64, or the accepted residual risk stated in the README), then its test. | REL-01 |
| G-011 | A PIN change and a sign-out end REST sessions at once, but the session store notifies nothing when a session ends, so a WebSocket joined to `dm` with that session would stay connected. No WebSocket exists yet. Found by the SRV-02 review, 2026-09-24. | Once LIV-01 adds the `dm` room, a device whose session a PIN change ended would keep receiving DM events and sending commands until it reconnects. | LIV-01 disconnects every socket of an ended session, with a test that a PIN change and a sign-out drop the other device's socket at once. | LIV-01 |
| G-012 | Deleting the live scene, or a session or campaign holding it, clears `settings.live_scene_id` (SRV-03, D-078), but no WebSocket exists yet, so nothing tells a connected player view to show the idle screen (`03` §7, `08` §4). | Once the player view shows live scenes (LIV-03), a TV would keep showing a deleted scene until it reconnects, if nothing sends the change. | LIV-04 sends the idle state to both rooms when a REST deletion clears the live scene, with a test that a connected player view switches to the idle screen and receives no id of the deleted scene. | LIV-04 |
| G-014 | The SRV-03 REST contract relies on the DM view for three things it cannot enforce, and no DM workspace exists yet (PRP-01): the error codes `reference_not_found`, `order_mismatch` and `confirmation_mismatch` (and SRV-02's) have no message in the catalogue; the delete dialog must show the counts and the live warning of `GET …/deletion` before sending them back; a create sent twice (a double click) makes two entities, because creation has no idempotency key. The confirmation proves the counts, not which rows: a tree whose contents changed but whose counts did not is deleted as confirmed. Found by the SRV-03 review, 2026-09-24. | Until PRP-01 there is no UI; after it, a missing mapping would show a raw code, and a careless dialog could delete without stating what goes. | PRP-01 maps every `ERROR_CODES` entry to the catalogue with a test, shows the deletion summary and live warning in the confirmation, and disables a create button while its request runs, each covered by a component or e2e test. | PRP-01 |
| G-015 | The display size can change only in the database: `regenerateDisplayVersions` (SRV-04, D-080) rewrites every display version and has its own test, but no route changes `display_variant_size` or starts it, and an upload that is being processed while it runs keeps the size it read when it started. | Until REL-01, a DM cannot tune the display size for the TV (`05` §7, G-002) without editing the database. | REL-01's settings screen changes the setting, starts the regeneration in the background and regenerates an image uploaded during the run, with a test. | REL-01 |
| G-016 | An uploaded image that no asset or scene has ever referenced is kept indefinitely: `03` §7 removes an image when nothing references it any more, which SRV-04 checks when a reference goes away (D-080), so a map uploaded and never used, or a library image whose asset was never created, stays on disk. | Abandoned uploads accumulate in the data directory, bounded by what the DM uploads. | SRV-05 and PRP-02 create the asset or set the scene map in the same action as the upload, with a test that an abandoned flow leaves no image, or a recorded decision that sweeps images never referenced. | SRV-05 |
